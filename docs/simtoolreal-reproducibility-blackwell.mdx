# Making SimToolReal Reproducible on Blackwell GPUs

GitHub: [sabdulmajid/simtoolreal](https://github.com/sabdulmajid/simtoolreal)

This project started with a practical research-engineering problem: the cloned SimToolReal repository was designed around the original Isaac Gym Preview 4 stack, but the machine I wanted to use has two NVIDIA RTX PRO 6000 Blackwell GPUs, each with roughly 96 GB of VRAM. Isaac Lab is installed on the machine, but the official SimToolReal codebase appears to target Isaac Gym, Python 3.8, PyTorch-era CUDA assumptions, and a repo-local fork of `rl_games`.

That combination is risky. A modern workstation can have excellent hardware while still being unable to run an older simulator binary stack. Before launching large training runs, I wanted to know exactly what works, what fails, what needs to be installed, and how every future result will be recorded.

The current milestone does not add a new algorithm. It does not port the environment to Isaac Lab. It turns the repository into a disciplined, reproducible research project where every smoke test, dry run, failure, and future training result has structured evidence behind it.

## First Principles

Scaling reinforcement learning experiments is not just a matter of increasing `num_envs`.

For a simulation-heavy robotics project, credible scaling depends on three things. First, the environment must actually launch under the intended simulator stack. Second, the training command must be reproducible, including git commit, seed, checkpoint, CUDA device, and software versions. Third, failures must be preserved as results, not erased from the record.

If a training run fails because `isaacgym` is missing, that is not a random inconvenience. It is a result that tells us the environment is not ready. If a dry-run command targets GPU1 with `CUDA_VISIBLE_DEVICES=1`, that is not performance evidence, but it is still useful evidence that the launch path is constructed safely. The goal of this phase was to separate those categories cleanly.

## What I Built

The work has three layers.

The first layer is a system audit. I added a read-only diagnostic script:

```bash
python scripts/check_system.py
```

It prints and saves a structured report to:

```text
reports/system_check.json
```

The report captures the OS, Python executable and version, git commit and dirty status, PyTorch version, CUDA availability, torch CUDA architecture list, GPU names and VRAM, `nvidia-smi` output, Isaac Gym import status, Isaac Lab import status, repo-local `rl_games` import status, required repository folders, pretrained policy files, and DexToolBench data availability.

The second layer is a safe reproduction harness. I added wrapper scripts for the standard lifecycle:

```text
scripts/download_assets.sh
scripts/run_pretrained_eval.sh
scripts/run_dextoolbench_eval.sh
scripts/train_scratch_smoke.sh
scripts/finetune_smoke.sh
```

These scripts are intentionally conservative. They create logs and reports, fail early on missing dependencies or assets, avoid GUI paths by default, and use bounded smoke settings instead of silently launching expensive jobs.

The third layer is a real compatibility environment path. The original repo wants Python 3.8 and Isaac Gym Preview 4, while the default shell on this machine is not that environment. I added:

```text
environment-simtoolreal-py38.yml
scripts/create_compat_env.sh
scripts/run_in_compat_env.sh
scripts/validate_compat_env.sh
```

The compatibility script creates or reuses:

```text
/pub7/neel2/conda_envs/simtoolreal-py38
```

It installs Python 3.8.20, torch 2.4.1+cu124, the SimToolReal package, the repo-local `rl_games` fork, and the wrapper dependencies needed for smoke tests. I also added an Isaac Gym acquisition script:

```text
scripts/download_isaacgym.sh
```

That script downloads the official Isaac Gym Preview 4 package outside the Git repo, extracts it under:

```text
/pub7/neel2/external/isaacgym_preview4/isaacgym
```

and records the action in:

```text
reports/download_isaacgym.json
```

The environment creator now auto-detects that extracted package and installs `${ISAAC_GYM_ROOT}/python` into the Python 3.8 compatibility environment. That matters because Isaac Gym Preview 4 is not just a normal pip dependency: its `setup.py` requires Python `<3.9`, and the package ships Python 3.8 binary bindings such as `gym_38.so`.

The fourth layer is GPU-scaling discipline. I added independent GPU launch and profiling utilities:

```text
scripts/launch_train_gpu0.sh
scripts/launch_train_gpu1.sh
scripts/sweep_num_envs.sh
scripts/profile_gpu_scaling.py
```

The current repo does not have verified true distributed multi-GPU training, so the safe first strategy is one process per GPU, pinned with `CUDA_VISIBLE_DEVICES`. The sweep targets the important environment counts:

```text
12288
24576
49152
```

Those counts respect the repository constraint that `num_envs` must be divisible by `num_blocks`.

## Experiment Discipline

The most important addition is the experiment ledger.

Every wrapper now writes or contributes to structured result files:

```text
reports/experiment_runs.jsonl
reports/experiment_results.csv
reports/experiment_results.json
reports/experiment_summary.md
```

Each recorded row includes the command, git commit, dirty git status, environment name, Python version, torch and CUDA versions, GPU id and name, `num_envs`, seed, scratch versus finetune mode, checkpoint path, start and end time, exit code, log path, peak VRAM, GPU utilization, throughput or FPS if available, and final metric or reward if available.

The aggregator is deliberately simple:

```bash
python scripts/aggregate_results.py
```

It reads the JSONL ledger and writes a CSV table, JSON table, and Markdown summary. The summary also includes a "Best Recorded Run" section. If a successful run exists, that section gives the exact command and environment evidence needed to reproduce it. If no successful run exists, the summary says so instead of pretending that a dry run is a result.

This matters because robotics simulation results are easy to overstate. A dry-run scaling command is useful, but it is not throughput. A failed import is a blocker, but it is still evidence. The ledger keeps those distinctions intact.

## Current Validation Results

The compatibility environment now exists, Isaac Gym Preview 4 is installed, and the system audit runs inside the environment. The latest report is:

```text
Python: /pub7/neel2/conda_envs/simtoolreal-py38/bin/python
Python version: 3.8.20
PyTorch: 2.4.1+cu124
CUDA available: true
GPUs: 2x NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition
VRAM: about 97887 MiB per GPU
```

The repo-local dependency state is materially better than the original broken shell:

```text
tyro: installed
rl_games.torch_runner: import OK from the repo-local fork
isaacgym: import OK from the extracted Isaac Gym Preview 4 package
pretrained_policy/config.yaml: present
pretrained_policy/model.pth: present
```

The pretrained checkpoint was downloaded successfully through the wrapper, and the checkpoint directory is ignored so it does not end up in Git. The missing Isaac Gym blocker is gone.

The remaining blocker is sharper and more important:

```text
torch CUDA arch list: sm_50, sm_60, sm_70, sm_75, sm_80, sm_86, sm_90
GPU capability: sm_120
CUDA kernel smoke: RuntimeError: no kernel image is available for execution on the device
```

This is not just a warning from inspection. The validation script now runs a tiny CUDA operation on the visible GPUs. On this workstation, torch 2.4.1+cu124 imports, sees the GPUs, and then fails to execute a CUDA kernel on Blackwell.

So the project is no longer blocked by the wrong Python version, missing `tyro`, missing pretrained policy files, missing Isaac Gym, or the local `rl_games` fork. It is blocked by the conflict between Isaac Gym's Python 3.8 requirement and the lack of a tested Python 3.8 PyTorch wheel that can execute kernels on `sm_120` Blackwell GPUs.

The smoke scripts behave correctly in this updated environment:

```text
download_assets: success
download_isaacgym: success
validate_compat_env: gpu_runtime_error, torch CUDA kernel cannot execute on sm_120
pretrained eval: gpu_runtime_error after reaching CUDA execution
DexToolBench eval: gpu_runtime_error after reaching CUDA execution
scratch smoke: gpu_runtime_error after reaching CUDA execution
finetune smoke: gpu_runtime_error after reaching CUDA execution
```

Those outcomes are recorded in the experiment result table. They are not lost in terminal scrollback, and failed runs are not silently dropped. The aggregator also preserves the specific failure class, so these rows are labeled `gpu_runtime_error` rather than generic failure.

## GPU Scaling Harness

The GPU scaling scripts have only been validated in dry-run mode so far. That is intentional. Since the compatibility environment cannot execute torch CUDA kernels on Blackwell, launching real scaling would not test throughput. It would only reproduce the kernel-image failure at larger scale.

The dry-run harness successfully generated commands for GPU0 and GPU1. The GPU1 sweep produced dry-run rows for:

```text
12288 envs
24576 envs
49152 envs
```

The aggregate report records these as `dry_run`, not as successful training. No throughput, peak SimToolReal VRAM, final reward, or steps per second is claimed.

This is the right level of evidence for the current state. The launch discipline exists. Real scaling still depends on resolving the Python 3.8 PyTorch/Blackwell runtime blocker.

## What We Did Not Claim

This milestone is intentionally strict about negative evidence.

I am not claiming that SimToolReal currently works on this machine. I am not claiming that Isaac Gym Preview 4 plus Python 3.8 PyTorch is compatible with Blackwell. I am not claiming any throughput number. I am not claiming that the repo supports distributed multi-GPU training. I am also not claiming Isaac Lab compatibility.

The current state is narrower and more useful: the repo now has a reproducible audit harness, an automated Isaac Gym install path, safe smoke scripts, dry-run GPU scaling tools, structured result aggregation, and clear blocker documentation with exact logs.

That makes the next step much cleaner. Instead of debugging from an ambiguous shell state, the next milestone can focus on the real compatibility decision: use non-Blackwell hardware for the original Isaac Gym stack, build or locate a Python 3.8 torch package that supports `sm_120`, or start a scoped Isaac Lab migration under a modern Python/PyTorch stack.

## Why This Matters

Research code often fails in two ways. It can fail technically, because a dependency is missing or a simulator binary is incompatible. It can also fail scientifically, because results are not recorded in a way that someone else can audit.

This milestone addresses the second problem before scaling into the first. Every command now has a place to put evidence. Every failure is labeled. Every future successful run should carry the environment, git state, command, checkpoint, seed, GPU identity, and metric trail needed to reproduce it.

That discipline is especially important for GPU scaling. Larger `num_envs` is not automatically better. The meaningful target is stable environment steps per second, reliable physics, useful checkpoints, and actual task progress per wall-clock hour. Filling VRAM is not the goal. Running credible experiments is.

## Next Step

The correct next milestone is no longer "install Isaac Gym." That has been done. The next milestone is to resolve the Blackwell runtime incompatibility.

```bash
bash scripts/validate_compat_env.sh
```

This currently fails with:

```text
status: gpu_runtime_error
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

If a Blackwell-capable Python 3.8 torch build is installed, the same scripts should be rerun in order:

```bash
bash scripts/run_in_compat_env.sh python scripts/check_system.py
bash scripts/run_in_compat_env.sh bash scripts/run_pretrained_eval.sh
bash scripts/run_in_compat_env.sh bash scripts/run_dextoolbench_eval.sh
bash scripts/run_in_compat_env.sh bash scripts/train_scratch_smoke.sh
bash scripts/run_in_compat_env.sh bash scripts/finetune_smoke.sh
```

If those smoke tests pass, then the repo is ready for real single-GPU smoke training, followed by independent GPU0 and GPU1 scaling sweeps. Until then, large `num_envs` runs would be noise.

## Summary

This phase turned SimToolReal from a cloned research repo into an auditable experiment workflow.

The project now has system diagnostics, a Python 3.8 compatibility environment builder, an Isaac Gym Preview 4 download/install path, safe reproduction scripts, independent GPU launch wrappers, dry-run scaling sweeps, structured JSON/CSV result aggregation, best-run reproduction documentation, pretrained policy asset handling, and clear blocker tracking. The original training stack is blocked by a proven Blackwell/PyTorch runtime mismatch, not by missing imports or ambiguous setup.

Before asking how far two 96 GB Blackwell GPUs can scale SimToolReal, the repository now asks a better question: can we prove exactly what ran, where it ran, and what happened?
